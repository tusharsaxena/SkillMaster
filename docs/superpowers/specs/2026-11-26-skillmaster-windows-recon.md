== LDB tooltip bug: why the expand/collapse chevron does nothing
F: Two causes. (1) By an earlier owner decision the window-style tooltip makes every header inert: stillHeader() calls EnableMouse(false) on the header and on all its marks including the chevron, so the chevron's HeaderMark onClick (Blocks.lua onHeaderClick -> B:ToggleCollapsed) and the header's own OnClick never fire. (2) Even with the mouse enabled, nothing would repaint the tooltip: the toggle sends LAYOUT_CHANGED, whose handler only refreshes the main window and detached windows, and BrokerPanel only fills on OnEnter. P: In stillHeader leave h.chevron mouse-enabled (header body stays inert so only the button acts); after the toggle, if P.Frame():IsShown() then P.Fill() while preserving state.offset (clamped) instead of SetScroll(0). Hook it in Blocks' relayout or a BrokerPanel bus target on LAYOUT_CHANGED. Since the collapse is the window's own layout.blocks[id].collapsed, a tooltip toggle also collapses the block in its window (and waits out combat through whenSafe). Update test_round6.lua:822-827.
Q: Should the tooltip's collapse be shared with the block's window (today's semantics: the chevron 'says the window's collapse') or a tooltip-only state (e.g. tooltips.ldb.collapsed[id]) so folding in the tooltip never changes the window? == (A) Reputations: API presence and data shape
F: CONFIRMED PRESENT (by name, and used by Blizzard's Forever ReputationFrame): C_Reputation.GetNumFactions, GetFactionDataByIndex, GetFactionDataByID, ExpandFactionHeader, CollapseFactionHeader, ExpandAllFactionHeaders, CollapseAllFactionHeaders, IsFactionActive, SetFactionActive, GetWatchedFactionData, GetSelectedFaction, IsAccountWideReputation, IsMajorFaction, GetFactionParagonInfo, Get/SetReputationSortType, AreLegacyReputationsShown, plus C_GossipInfo.GetFriendshipReputation and C_MajorFactions.*. ABSENT: the bare GetNumFactions, GetFactionInfo, GetWatchedFactionInfo, ExpandFactionHeader and CollapseFactionHeader. GetFactionDataByIndex answers ONE TABLE, FactionData, with these fields: factionID, name, description, reaction (luaIndex 1-8), currentReactionThreshold, nextReactionThreshold, currentStanding, atWarWith, canToggleAtWar, isChild, isHeader, isHeaderWithRep, isCollapsed, isWatched, hasBonusRepGain, canSetInactive, isAccountWide. There is no hasRep field; use isHeaderWithRep instead. The header/child structure is two levels, exactly as the panel shows it. A top-level header is isHeader and not isChild (for example 'Alliance' or 'Other'). A sub-header is isHeader and isChild (for example 'Steamwheedle Cartel'), and it can carry its own bar when isHeaderWithRep is true. A child of a sub-header is not isHeader and isChild. A plain faction is neither. The bar is min = currentReactionThreshold, max = nextReactionThreshold, value = currentStanding, normalised so that min is 0. reaction == 8 (MAX_REPUTATION_REACTION, Exalted) is drawn as a full bar. The standing label is GetText('FACTION_STANDING_LABEL'..reaction, UnitSex('player')) and the colour is FACTION_BAR_COLORS[reaction]. A faction can also be a friendship (C_GossipInfo.GetFriendshipReputation(id).friendshipFactionID > 0) or a major faction (renown), and each has its own bar maths. Forever's PvP rank is itself a major faction (PVP_RANK_POINTS_FACTION_ID, read through C_MajorFactions.GetMajorFactionProgressionInfo), so it may appear in the faction list.
P: Write RepData as a sibling of SkillData and StatData that reads GetFactionDataByIndex into a model of {header -> sub-header -> faction}, keyed by factionID, and announces REPS_UPDATED. Give a sub-header with isHeaderWithRep its own bar. Handle three bar kinds (standard, friendship, major faction) and show only standard until the probe shows that the others occur on Forever. Use the client's FACTION_STANDING_LABELn globals and FACTION_BAR_COLORS for labels and colours, with no hard-coded English.

== (A) Reputations: the collapse-state trap and a safe read strategy
F: Header collapse state is CLIENT state shared with Blizzard's ReputationFrame. GetFactionDataByIndex enumerates only what is visible, and the children of a collapsed header are not in the index range. Blizzard's own panel toggles headers with C_Reputation.ExpandFactionHeader and CollapseFactionHeader(factionIndex). So if our reader expands a header and leaves it open, the player's panel changes, and if our UI collapses through the API, it collapses the player's panel. Expanding also shifts every index below the header and fires UPDATE_FACTION, which risks re-entering our own handler. The sort type and the legacy filter (C_Reputation.SetReputationSortType, SetLegacyReputationsShown) also change the list, but the Forever panel hides its filter UI (ShouldShowFilters returns false). SkillMaster already solves the same trap for skills: it expands every collapsed header, reads, then re-collapses bottom-up so the earlier indices do not move. LootHistory deliberately does NOT expand the currency list, for exactly this reason. The other route is GetFactionDataByID(factionID), which reads one known faction without touching any state.
P: Reuse the SkillData pattern. Do a full expand-read-restore pass only on the first build, after login and out of combat, never while ReputationFrame:IsShown(). Record the opened headers by factionID, re-collapse them bottom-up, and suppress our own UPDATE_FACTION handler for the duration (a reentrancy latch). Cache factionID -> {header, sub-header} in the per-character SavedVariables. On later UPDATE_FACTION events, refresh each known faction with GetFactionDataByID, which touches no state, and rerun the full pass only when GetNumFactions changes with every header expanded. Our window's own fold state is addon-side (db), and it NEVER calls Expand/CollapseFactionHeader.
Q: Does GetFactionDataByID answer for a faction whose header is collapsed? On Retail it does; on Forever, the probe should call it for a child of a collapsed header.

== (C) Statistics: APIs, signature and nesting
F: CONFIRMED PRESENT by name: GetStatisticsCategoryList, GetCategoryInfo, GetCategoryNumAchievements, GetAchievementInfo, GetStatistic, GetCategoryList, GetAchievementCategory and GetAchievementCriteriaInfo. Blizzard's Forever StatisticsFrame shows how to use them, and its signatures DIFFER from the Retail habit. GetStatistic is called as GetStatistic(categoryID, statIndex) and answers `quantity, skip, statID`. Retail's form is GetStatistic(achievementID), which answers a display string. Blizzard skips a row when `skip` is set or statID is nil, takes the name from select(2, GetAchievementInfo(statID)), and shows tonumber(quantity) > 0 or '--'. The row count is GetCategoryNumAchievements(categoryID). For nesting, GetCategoryInfo(categoryID) answers name, parentCategoryID, and a parent of -1 is a root. GetStatisticsCategoryList() answers a table that Blizzard orders by numeric key, which allows for sparse keys. Blizzard builds an arbitrary-depth tree (roots, then children recursively) with categories interleaved with their stat rows. Depth 1 uses a header template, and depth 2 or more uses a sub-header with its own collapse button, giving multi-level folding such as Character > Wealth. The fold state is a pure client-side tree, with no server or panel state, so there is NO collapse trap for this family. There is no C_ namespace for statistics, and AchievementInfoDocumentation lists only C_AchievementInfo helpers and events.
P: StatisticsData builds the category tree once (cheap: one GetStatisticsCategoryList call and one GetCategoryInfo per category) and stores it as {id, name, parent, children}. Write the reader against the Forever signature GetStatistic(categoryID, index) -> quantity, skip, statID, with a presence test, and keep the raw quantity. Display it as Blizzard does (a number, or '--'), and keep a string quantity verbatim in case Wealth answers a money string. Multi-level folding is addon-side db state keyed by categoryID, with every category collapsed by default.

== (C) Statistics: events, read cost and a lazy, fold-driven strategy
F: The only refresh event Blizzard uses is CRITERIA_UPDATE (documented, no payload). It registers it only while the frame is shown (OnShow and OnHide), and on each event it rebuilds the WHOLE tree, so Blizzard treats a full read as affordable while the tab is open. CRITERIA_UPDATE is noisy: it fires on many unrelated criteria changes and gives no category, so you cannot tell which stat changed. Without the probe the row count is unknown. Retail has about 1000 statistics, and Forever's list is probably smaller but is still 'many hundreds' in the worst case. Reading a row costs two API calls (GetStatistic plus GetAchievementInfo), and the names are static, so they can be cached once.
P: Read lazily, driven by folds. (1) At login, read nothing beyond the category tree, and only when the Statistics window or its broker is first used. (2) When a category is unfolded, read its rows: cache name and statID per row for the session, and read the values. (3) Register CRITERIA_UPDATE only while the Statistics window or tooltip is visible, coalesce it to at most one refresh per ~1 s through a one-shot timer (an event-triggered debounce, not a poll, which keeps to the addon's read-on-change rule), and re-read only the unfolded categories plus pinned statistics. (4) While hidden, a pinned statistic in the broker feed refreshes on CRITERIA_UPDATE with the same debounce, reading just that one row by its (categoryID, index), with the index re-resolved by statID if it moved. (5) Add a perf-scenario ceiling for a full read in the headless kit, with a fixture of about 1000 rows.

== Separate windows and brokers, and the LDB tooltip fold (relevant to the data shape)
F: Two of the three families carry their own nested header structure from the client: reputations with two levels (header and sub-header with a bar), and statistics with arbitrary depth. Currencies have depth-based headers. A per-family window therefore needs a tree-capable row model, unlike today's flat skill and stat groups. Blizzard's own Forever panels keep the fold state on the row's tree node (statistics) or in the client (reputations and currencies). For our windows and LDB tooltips, the fold must be addon-side state for all three families, so that clicking a category in our tooltip never calls ExpandFactionHeader or ExpandCurrencyList.

Make the LDB tooltip's category toggle flip only this store, then re-render. That is the single interaction the owner wants to keep in the tooltip.
